# Правила кода фронтенда

## Имена

- Переменные и функции — `camelCase`: `selectedGame`, `loadGames`.
- Компоненты и классы — `PascalCase`, имя файла совпадает с экспортом: `GameCard.jsx`, `HttpClient.js`.
- Хуки начинаются с `use`: `useGameEditor`.
- Константы конфигурации — `UPPER_SNAKE_CASE`: `DEFAULT_TIMEOUT_MS`.
- Булевым значениям даём имена, раскрывающие смысл проверки: `isDemo`, `isPublished`, `hasMore`. Не меняем существующие публичные пропсы ради косметического переименования.
- В обработчиках используем `event`, в списках — `game`, `message`, `version`, `index`. Короткие `x`, `y`, `i`, `j` допустимы для координат и локальных счётчиков.
- Локальный обработчик события — `handleSubmit`; callback-проп компонента — `onSubmit`.
- Имена полей серверного JSON сохраняются по контракту API. Например, `access_key` не переименовывается внутри отправляемого запроса.

## Структура и ООП

- React-компоненты функциональные. Их состояние и жизненный цикл обслуживают React-хуки.
- Объекты с собственным состоянием и связанными операциями оформляем классами, когда это делает код понятнее.
- `HttpClient` инкапсулирует адрес, токен и HTTP-логику в приватных полях. `PlatformApi` получает этот клиент через конструктор и содержит методы платформы. Это композиция; зависимости можно заменить в тестах.
- Наследование используем только для реального отношения «является». Базовые классы, фабрики и универсальные обёртки без практической необходимости не добавляем.
- Компонент отвечает за разметку и взаимодействие, хук — за сценарий и состояние, API-сервис — за запросы. Один модуль не совмещает все эти обязанности.
- Чистые функции форматирования и фильтрации остаются обычными функциями.

## Оформление

- Ветки `if`, `else` и тела циклов оформляем фигурными скобками.
- Используем ранний выход, когда он уменьшает вложенность.
- Независимые функции отделяем пустой строкой. Связанные шаги внутри длинной функции объединяем в небольшие смысловые блоки.
- Не вкладываем сложную бизнес-логику в JSX. Вычисления и обработчики должны читаться отдельно от разметки.
- Комментарий объясняет причину решения или ограничение. Очевидные действия повторно не описываем.
- Неиспользуемый код и импорты удаляем. Не добавляем код «на будущее» без задачи.
- Форматирование выполняет `npm run format`; проверяет `npm run format:check`.

Перед сдачей изменения выполняем `npm test` и `npm run build`. Для изменений поведения дополнительно проверяем соответствующий пользовательский сценарий.
